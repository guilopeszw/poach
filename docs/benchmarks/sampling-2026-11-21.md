# Batched sampling benchmark — 2026-11-21

Baseline: `a3a48b19e49c2485e3130c20a4a7af53def1eda5`. Candidate sampling implementation: `0d68021` (runtime enablement and harness cleanup do not change analysis). macOS 26.6.2 arm64, Homebrew FFmpeg 9.0.2. Local synthetic fixtures only. One warm-up and five alternating measured runs per implementation; end-to-end Node startup included. Exact normalized JSON and decoded PNG pixel parity passed on every run. Images are decoded to RGB PAM, including dimensions, before hashing.

Full min/median/max wall time, CPU, process counts and separately sampled parent/largest-child RSS are in the adjacent JSON. CPU uses wait4 and includes waited descendants. RSS is sampled, not an exact high-water mark or sum of children; short processes can be missed. This is a shared workstation: exploratory runs overlapped some early cases and ordinary development activity occurred during the run. Treat timings as observed results rather than isolated laboratory estimates. Repeat before release with the bundled tools and real ScreenCaptureKit media. Sparse synthetic recordings exercise held frames but are not proof of native capture parity.

Reproduce: build the core at the baseline commit in a separate checkout and build the candidate, then run `python3 scripts/bench/compare.py BASELINE_ROOT CANDIDATE_ROOT 5`. It generates temporary fixtures, wraps FFmpeg/ffprobe for process counts, compares outputs and prints JSON lines. This does not measure the app's stop-to-editor latency.
