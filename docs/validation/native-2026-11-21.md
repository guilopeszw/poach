## Stop-to-editor latency

Metric: the app's existing `Recording stop requested` → `Review editor presented` CaptureLifecycle log events. This includes recording finalization, normalization/analysis and editor setup. It excludes input dispatch before the stop handler and does not measure physical-display first paint. The native editor was visually confirmed after every run.

One manually stopped warm-up was excluded. Five measured recordings used the configured 30-second auto-stop, the same 1512×949-point local Chrome window, and the same synthetic upload interaction. No competing test/build workload ran during the measured stops. This is a shared developer workstation measurement, not a cross-machine performance guarantee or comparison against the original native app.

## Native UI and evidence checks

- Selected only the isolated local synthetic dropzone Chrome window; no whole-desktop capture. The recorded interaction and resulting editor were visually verified. All six originals contain one video stream and no audio. Native pointer polling produced 3,411 samples/12 button-held samples on the warm-up and 3,723/19 on the last measured recording.
- A real ScreenCaptureKit variable-frame-rate recording (28.900s, 841 frames) passed exact normalized analysis and reference-PNG byte parity against original main `a3a48b19e49c2485e3130c20a4a7af53def1eda5`, with the same bundled FFmpeg binary for both implementations.
- Recorded video reports 1920×1204 pixels, 1512×949 macOS points, horizontal stored-pixel scale 1.269841. Native screenshot reports 3024×1898 pixels for the same 1512×949-point window, scale2. The returned 1280×803 video previews are captioned separately from source dimensions.
- Copied the native recording handoff through the actual app UI and read its matching ID through Poach MCP. The packaged server returned the real notes, pointer evidence and capture metadata. A 97×73 crop at (65,43) matched exactly those RGB rows in the full native frame.
- Took the native Retina screenshot, saved it as a favorite, exported `.poach`, imported it through the native file picker, and copied the imported favorite's handoff. Its 3024×1898 source dimensions,1512×949 point dimensions and 2× scale survived the round trip. It has no original source path; its actual saved preview is 1152×723 pixels.
- Removed only the two test-owned favorite records and verified the copied handoff image remained byte-identical and readable through the packaged MCP server. Existing favorites were preserved. Native brief directories are 0700 and files 0600.
- Closed the isolated test browser window and restored the app's original Record/Screen area selections. Synthetic artifacts and the portable screenshot handoff are retained in the local review folder; no personal screen media was published.

## Reproduce

1. Build with `bash scripts/build-macos-app.sh`, launch that exact package and grant/use its existing Screen Recording permission.
2. Serve `apps/benchmark` locally on 127.0.0.1:8741. Open it in an isolated Chrome window. Record only that app window, trigger mood.png's simulated upload and let the configured 30s limit stop each measured run.
3. Capture `log stream --style ndjson --level info --predicate 'process == "Poach" AND subsystem == "dev.poach.app" AND category == "CaptureLifecycle"'`. Exclude one warm-up; pair the stop/finalized/analyzed/editor events by recording, and subtract timestamps. Keep input and display-latency exclusions explicit.
4. Confirm the editor after every run; share through the local Copy prompt action. Verify the matching ID, dimensions, odd-origin crop pixels and normalized end boundary through the packaged MCP server. Repeat native screenshot→favorite→export→import→copy with synthetic media.
